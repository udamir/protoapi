# Changelog

## 0.1.0 (unreleased)

First release: ProtoApi 0.1 format, `buildFromProto`, `buildFromProtoAsync`, `buildFromDescriptorSet`, `buildFromDescriptorSetBinary`, `printProto`, `locatePointer`, `locateDiff`, bundled definitions (protobuf v36.2, protobuf-go v1.36.12 `go_features.proto`, googleapis, protovalidate v1.2.2, protoc-gen-validate v1.3.3, grpc-gateway v2.33.0). Edition 2026; edition defaults read from `FeatureSetDefaults`; `protoapi/core` entry without the bundled sources; `browser` points at the ESM build; binary sets decode custom options with a per-file registry (set + bundle); `@bufbuild/protobuf` peer >= 2.8.0.

Text producer: protoc's import-visibility-aware name lookup and edition 2024+ symbol visibility (`EXPORT_TOP_LEVEL`, `LOCAL_ALL`, `EXPORT_ALL`, `STRICT`); `import option` types only in options; definition checks with the new issue code `invalid-definition` (syntax and edition rules, naming styles, removed options, import cycles) plus value, kind, number and name checks with the existing codes; `BuildOptions.tabWidth` (default 4, buf's columns); keyword type names, long string literals and syntax-error files handled as buf does; the async loader discovers imports by parsing and never rejects. `ProtoApiFile.syntax` is absent for a file whose syntax could not be read.

Imports: the new option `imports` chooses what is emitted, and its default `"user"` replaces the earlier default. The entry files and every file you supply (`sources`, the loader) that they reach through any import are emitted in full; files resolved from the bundle (built-in or the `bundle` option) contribute only the declarations referenced from emitted ones. `"referenced"` is the earlier default (`includeImports: false`), `"all"` emits everything (`includeImports: true`). `includeImports` stays as a deprecated alias; passing it together with an `imports` value of another meaning throws a `TypeError`. A bundled file that is not an entry is marked `bundled: true` in `files` (in every mode), carries no header `description` (the licence comment of the bundled sources is dropped), and is not printed by `printProto`, so a document built with `"user"` rebuilds from the printed files alone. Descriptor sets: a file counts as bundled when its path is a key of the bundle in effect, so `protoapi/core` emits a set's googleapis or protovalidate files in full.

Requiredness: annotation-level requiredness is the field keyword `required: true`, and messages no longer carry a `required` array of field names. Every source sets it on the field: `@Required`, the `Required.` prefix, `(google.api.field_behavior) = REQUIRED`, `(buf.validate.field).required`, PGV `(validate.rules).message.required`, and `openapiv2_schema.json_schema.required` on each field it names (by proto or JSON name; unmatched names stay under the message's `options`), extensions included. A conflict on `required` (for example `OPTIONAL` against a tag or `json_schema.required`) is recorded on the field. A `required` label or `LEGACY_REQUIRED` stays `presence: required` and never sets the keyword. In the key order `required` comes first among the annotation keywords of a field. The source map has an entry `…/properties/<field>/required` (the option, tag or prefix line, or the message's `openapiv2_schema` statement), and `locateDiff` no longer maps an index into a message `required` array to the field. `printProto` prints the field keyword as before. The format version stays `0.1`.

Scalar types: a scalar position (field, `items`, map key and value) writes the protobuf scalar type in `type` (`type: int64`, `type: bytes`); the JSON Schema category (`integer`, `number`, `boolean`, `string`) and the separate `protoType` key are gone. `array` and `object` on fields, and `object` / `string` on message and enum components, are unchanged. The format version stays `0.1`.

Comments: leading, trailing and detached comments are attached as buf 1.75 attaches them, in every layout, so the text producer and a buf-built descriptor set give the same descriptions. protoc attaches differently only in rare layouts: a block comment after a declaration's `;` or a block's `}` followed by a newline leads the next declaration; a block comment between `{` and `}` on one line trails the block (or the last declaration before `}`); a block comment followed by a `//` comment on the declaration's line trails the declaration and the `//` comment leads the next one; a block comment that ends on the line of the next token leads nothing; a `//` group between a same-line trailing comment and a blank line, and comments after the last token of a file, are attached to nothing.

Final cleanup: a same-line block comment followed by more comments before `}` no longer gives a syntax error; a text-format `Any` written with `type_url` / `value` fields is decoded and written in the expanded form, as the descriptor producer gives it; an unknown sub-path option `(unk.sub).x` is kept as `unk.sub: { x }` and printed back as written, and an unknown option without a dot prints in parentheses; faster `buildFromDescriptorSet` (SourceCodeInfo index).
